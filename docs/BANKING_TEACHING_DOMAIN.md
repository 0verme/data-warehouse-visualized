# 统一银行教学业务域（Banking Teaching Domain）

> **状态：初版教学 Domain Contract / Single Source of Truth**
>
> 本文件约束后续课程规划、课程文案和交互 Demo 中如何使用银行业务对象。它不是生产银行数据模型、监管模型或数据库建表方案。

## 1. Why：为什么需要统一业务域

仓库当前的课程已经使用了订单、用户、商品、支付等电商案例，并围绕这些案例建立了分层、粒度、指标、SQL、调度、质量、血缘、治理、湖仓和性能实验。现有内容不因本文件而被一次性重写。

后续课程需要一条连续的业务线：学习者可以看到同一批业务对象如何经过业务系统接入、仓库分层、建模、指标定义、SQL 加工、日批调度、质量检查、血缘追踪、治理和架构取舍。银行业务适合承载这条连续链路，因为客户、账户、交易、贷款和收单都能产生真实的数据工程问题，同时仍可以用很小的样本讲清楚 Grain、时间和口径。

采用银行业务的目的不是增加金融知识门槛，也不是把 sql.sb 变成银行业务培训网站。它的作用是减少每个 Issue、PR 或 Agent 重新发明业务世界的成本，让跨课程的主键、行含义和字段语义能够被复用和追踪。

### 当前基线与采用边界

- 当前已上线课程仍以订单域为主，现有 `src/content/lessons/` 和可视化实验保持不变。
- 后续新课程或章节重构优先参考本文件；第 03 章数据建模已通过 #56 作为第一批全面采用银行教学域的章节。
- 第 04–11 章逐步消费相同的业务对象和语义；第 12 章综合实战再把它们组合起来。
- 已经成熟且没有明确收益的订单课程，不因为统一场景而强制改写；通用案例能更清楚地解释某个技术知识点时，可以继续使用。

## 2. Core principle

> **银行场景是教学载体，不是教学目标。**

教学目标、学习负担和技术概念优先于银行业务真实性。每次引入银行术语，都要先给出足够简单的业务解释；不要求学习者先懂银行，才能学习数据仓库。

## 3. 第一阶段范围

第一阶段只维护一组足以串起课程的核心对象：

```text
Customer        客户
Account         账户
Transaction     账户交易
Branch          机构
Product         产品

LoanContract    贷款合同
LoanNote        借据 / 实际放款
Repayment       还款

Merchant        商户
AcquiringTransaction
                收单交易
```

第一阶段暂不引入监管专业概念、完整会计科目体系、五级分类、表内外业务、票据、银团、贴现、真实核心系统内部实现或其他生产级银行对象。只有当某个知识点确实需要时，才按“新增对象规则”单独讨论。

## 4. Canonical Entities

Canonical name 是跨课程稳定的逻辑对象名。下表中的 identity 是教学业务标识，不限制仓库内部是否另外使用 surrogate key；使用 surrogate key 时仍需保留并说明对应的业务标识。

| Canonical entity       | 中文            | 最小业务解释                                                                                   | 稳定 identity / 默认 Grain                                                                                   |
| ---------------------- | --------------- | ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `Customer`             | 客户            | 与银行发生关系的个人或组织。第一阶段只关心用于分析的基本客户身份与属性。                       | `customer_id`；一行代表一个客户逻辑身份。需要历史属性时，用版本化维度表达，不改变客户 identity。             |
| `Account`              | 账户            | 客户持有、可发生账户交易的银行账户。第一阶段默认一个账户归属于一个客户，并关联一个机构和产品。 | `account_id`；一行代表一个账户。账户余额是状态，不等同于账户交易流水。                                       |
| `Transaction`          | 账户交易        | 账户上发生并被记录的一笔存入、支出、转账、费用或调整等交易事件。                               | `transaction_id`；一行代表一笔账户交易，金额和发生/入账时间必须与该事件 Grain 对齐。                         |
| `Branch`               | 机构            | 银行的分支机构或分析所需的机构节点，用于组织归属和经营分析。                                   | `branch_id`；一行代表一个机构节点。机构层级如需展开，应另行声明，不把层级细节隐含在名称中。                  |
| `Product`              | 产品            | 银行向客户提供的存款、贷款或其他教学范围内的产品定义。                                         | `product_id`；一行代表一个产品定义。产品不是账户、合同或借据。                                               |
| `LoanContract`         | 贷款合同        | 客户与银行约定的贷款条款、额度或合同关系。合同成立不代表已经发生实际放款。                     | `contract_id`；一行代表一份贷款合同。`contract_amount` 是合同约定金额，不直接当作已放款本金。                |
| `LoanNote`             | 借据 / 实际放款 | 某份贷款合同下的一次实际放款或借据记录，用来承载实际形成的贷款本金。                           | `note_id`；一行代表一笔借据/实际放款，并通过 `contract_id` 归属合同。                                        |
| `Repayment`            | 还款            | 针对借据记录的一笔实际还款流水，包含还款发生时间和实际偿还金额。                               | `repayment_id`；一行代表一笔还款记录，并通过 `note_id` 归属借据。还款计划项不是本对象的默认含义。            |
| `Merchant`             | 商户            | 接入银行收单服务、发生收单交易的商户。                                                         | `merchant_id`；一行代表一个商户。第一阶段不默认把商户等同于客户。                                            |
| `AcquiringTransaction` | 收单交易        | 商户侧发生的一笔收单交易，用于描述交易金额、时间、状态和商户归属。                             | `acquiring_transaction_id`；一行代表一笔收单交易。它不自动等同于 `Transaction`，也不自动等同于支付结算流水。 |

### 最小关系

```text
Customer
  └─ Account
       └─ Transaction

Customer
  └─ LoanContract
       └─ LoanNote
            └─ Repayment

Branch
  ├─ Account
  ├─ LoanContract
  └─ Transaction（通常通过 Account 归属；若直接带机构字段，需说明语义）

Product
  ├─ Account
  └─ LoanContract

Merchant
  └─ AcquiringTransaction
```

关系的含义是教学上的最小关联，不代表生产系统只能有这些关系：

- `Account` 通过 `customer_id` 连接 `Customer`，通过 `branch_id` 和 `product_id` 连接机构、产品；共同账户等复杂情况不在第一阶段默认范围内。
- `Transaction` 的直接归属是 `Account`。如果需要按机构汇总，可以沿账户归属或明确的交易机构字段分析，不能在不同课程中随意改变 `branch_id` 的含义。
- `LoanContract`、`LoanNote`、`Repayment` 是一条信贷业务链。合同金额、实际放款本金、已还金额和贷款余额是不同业务量，不能用一个 `amount` 互相替代。
- `AcquiringTransaction` 只与 `Merchant` 建立默认关系。若未来需要解释收单资金入账到账户，必须明确事件、结算关系和 Grain，不把两种交易直接 Join。

## 5. 事实形态、identity 与 Grain

### 5.1 事实形态不能混用

同一个对象可以在不同课程中产生不同的分析产物，但每个产物必须单独声明 Grain：

| 形态                  | 一行代表什么                           | 银行教学例子                                                                | 不能怎样用                                                         |
| --------------------- | -------------------------------------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| Transaction fact      | 一笔在某个时间发生的事件               | `Transaction`、`AcquiringTransaction`、`Repayment`                          | 不能把事件金额直接当作期末余额；重复事件要先定义去重语义。         |
| Periodic snapshot     | 一个对象在固定周期末的状态             | `Account × snapshot_date` 的日终余额、`LoanNote × snapshot_date` 的贷款余额 | 不能跨多个日期直接 `SUM` 当作一笔业务金额；必须说明状态日期。      |
| Accumulating snapshot | 一个业务过程从开始到结束的生命周期记录 | 一笔 `LoanNote` 的放款、首次应还、首次还款、逾期、结清等里程碑              | 不能把生命周期的一行当成多笔交易；新增里程碑也不等于新增交易事件。 |

`Transaction`、`Snapshot`、`Lifecycle` 是不同的事实语义。课程需要使用哪个形态时，应同时写出：业务过程、行含义、identity、时间字段、可加度量和不适用的问题。

### 5.2 稳定 identity 与仓库 key

- `customer_id`、`account_id`、`transaction_id`、`branch_id`、`product_id`、`contract_id`、`note_id`、`repayment_id`、`merchant_id`、`acquiring_transaction_id` 是第一阶段推荐的逻辑 identity。
- 业务 identity 用于解释去重和跨层关联；维度需要保留历史时，可以增加 surrogate key 和有效时间区间，但不得因此改变原业务对象的含义。
- 同一个 identity 在 ODS、DWD、DWS、ADS 中可能作为原始键、外键或聚合维度出现；每层都要重新声明该层的 Grain，不能因为字段名相同就假设行含义相同。
- `LoanContract` 和 `LoanNote` 必须保持两个 identity。`contract_id` 表示约定关系，`note_id` 表示实际放款；一份合同可以对应多笔借据，除非某个教学案例明确限定为一对一。

### 5.3 时间与金额

推荐使用清楚的时间名：

- `business_date`：业务归属日期，用于日批和分区；不等于数据到达日期。
- `event_time` / `posted_at`：事件发生或入账时间，需说明当前课程采用哪一个。
- `snapshot_date`：状态快照所属日期。
- `arrived_at`：数据进入平台的时间，用来讲迟到和补数，不能替代业务日期。

金额字段要带业务含义，例如 `contract_amount`、`disbursed_principal`、`repayment_amount`、`transaction_amount`、`balance`。课程中的正负号、退款/冲正处理、币种和是否含费用必须在案例里说明；不要把所有金额都简称为 `amount` 后跨课程复用。

### 5.4 SCD 与历史属性

当问题需要回答“当时的客户/机构/产品属性是什么”，才考虑维度历史策略：

- **覆盖更新（SCD Type 1）**：直接用新值替换当前属性，适合只关心当前状态的字段。
- **拉链表（SCD Type 2）**：关闭旧版本并插入新版本，用有效时间区间保存历史属性，适合需要还原“当时”状态的字段。

拉链表的版本行不是新的客户或账户业务事件；关联条件应同时说明业务 identity、surrogate key（如有）和有效时间区间。第一阶段不把所有属性都默认做成拉链表。

## 7. 场景使用原则

1. 不进行一次性全站银行化重写；从后续新课程和章节重构开始逐步采用。
2. #56「03 数据建模」作为第一批全面采用银行教学域的章节，后续 #61、#60、#53 等章节继续消费同一批对象。
3. 已有成熟课程没有明确收益时，不因为统一场景而强制重写。
4. 同一实体跨章节的业务语义、identity、Grain 和字段含义尽量稳定；如发生变化，必须显式说明。
5. 新增对象前，先确认现有 Canonical Entity、关系或派生产物是否已经可以表达这个知识点。
6. 银行业务复杂度不能高于当前教学目标本身；简单案例优先于不必要的专业细节。
7. 如果通用技术案例更清楚，可以不强行银行化，并在课程规划中说明保留通用案例的原因。
8. 不允许把 `order` 机械改名为 `loan`。场景必须真正帮助学习者理解当前知识点，并保留正确的业务关系和时间语义。
9. 课程正文第一次出现银行术语时要给出简单解释；不把领域背景变成学习数仓的前置考试。
10. Demo 可以抽象和缩小数据，但不能为了方便交互而悄悄改变核心对象的 Grain 或金额含义。

## 8. 新业务对象的引入规则

引入一个不在本文件中的对象前，Issue 或 PR 必须先回答：

1. 它服务哪个明确的教学目标，现有对象为什么表达不了？
2. 它的中文名、Canonical name、stable identity 和默认 Grain 是什么？
3. 它与现有对象的基数关系、时间语义、金额语义和边界是什么？
4. 它会影响哪些章节、指标、SQL、调度、质量、血缘或治理示例？
5. 为什么不能用现有对象的派生视图、快照或生命周期记录替代？
6. 它的 Non-goals 是什么，如何控制银行业务复杂度？

确认需要新增后，应在同一个设计变更中更新本文件，并在 PR 中说明影响范围。不得在单个课程、Demo 或 Agent 任务里建立一套不受本文件约束的平行业务模型。特别是：

- 需要讨论还款计划时，先明确它与实际 `Repayment` 流水的区别；本阶段课程不新增还款计划实体，也不能让 `Repayment` 在不同课程中一会儿表示计划、一会儿表示实际还款。
- 需要客户与账户多对多、复杂机构层级、结算关系或监管属性时，先把它当作新增教学决策，不通过字段偷偷引入。
- 如果只是换了仓库层、聚合周期或事实形态，应新增产物的 Grain 说明，不要新增一个看似不同的业务实体。

## 9. Non-goals

本教学业务域不负责：

- 本轮重写全部现有课程或改变 01–12 的顺序。
- 构造生产级银行数据模型、监管数据集市或企业级 Canonical Data Model。
- 模拟真实银行核心系统、真实账户体系、真实 IAM 或生产银行业务逻辑。
- 一次性迁移现有电商课程，或把所有通用技术案例都改成银行案例。
- 设计几十张表、几百个字段、完整会计科目、五级分类、表内外业务、票据、银团或贴现等复杂体系。
- 为了统一业务域新增复杂基础设施、数据库、Dataset Registry 或真实数据接入。
- 把银行术语数量当作课程深度，或要求学习者先学习银行专业知识。

## 10. Naming / terminology 原则

- 跨课程文档优先使用 Canonical English name + 首次出现时的简明中文，例如 `LoanContract（贷款合同）`。物理表名可以使用 `dim_`、`fact_` 和 lower `snake_case`，但必须附带 Canonical entity 与 Grain，不要求物理表名和逻辑对象一一相同。
- 默认将 `Transaction` 解释为账户交易；涉及商户收单时使用完整的 `AcquiringTransaction（收单交易）`，不要用模糊的“支付流水”代替两者。
- `LoanContract` 是合同约定，`LoanNote` 是合同下的实际放款/借据，`Repayment` 是实际还款流水；三者不能互换或合并成一个 `loan`。
- `balance` 表示某一时点或期间末的状态时，必须带 `snapshot_date` 或等价时间语义；余额快照不能与发生额交易事实混称。
- `business_date`、事件时间、快照日期和到达时间分别命名；日切、迟到和补数示例必须明确采用哪一个日期。
- 银行术语第一次出现在课程正文或 Demo 说明时，先解释业务含义，再使用英文缩写或专业名词。代码和字段名可以保持稳定英文，但不能让字段名代替教学解释。
- 文档、课程、Demo 和 Issue 中若使用非 Canonical 别名，必须注明它对应的 Canonical entity 和 Grain；不使用 `user`、`member`、`client` 等相近词隐式创造多个客户对象。

## 11. 维护方式

本文件是后续课程规划、内容编写和交互 Demo 的业务域 Single Source of Truth。`CONTRIBUTING.md` 与 Pull Request 模板提供最小执行检查。

当课程需求与本文件冲突时，先在规划 Issue 中讨论教学必要性，再选择以下方式之一：复用现有对象、增加明确的派生产物、提出新的 Canonical entity，或保留通用案例。不要在代码或课程正文中静默分叉。任何确认后的 identity、Grain、关系或术语变化都应同步更新本文件，并说明受影响的章节。
